# Phase 1: feasibility result

Setup: Minecraft 26.3 client jar (SHA-1 e877b6a0..., class version 69 = Java 25), all non-native
libraries from the version JSON, TeaVM 0.16.0, WASM GC backend, entry point
`net.minecraft.client.main.Main`. Project: `mc-web/feasibility/`. Jar and tooling live in
`mc-web/work/` (gitignored, never committed).

## What works
- TeaVM reads the Java 25 class files and the whole dependency graph (client, Guava, Netty,
  DFU, Brigadier, fastutil, JOML, ICU, LWJGL Java classes, ...) without parser crashes.
- The compile needs a large heap (default ran out; `-Xmx24g` worked, about 2 minutes).
- Dependency analysis finishes and reports a closed list of what is missing, rather than failing
  on the first problem.

## What fails (analysis errors, not yet runtime behaviour)
About 96 distinct missing items, nearly all JDK APIs that TeaVM's class library lacks:

| Area | Examples |
|---|---|
| Concurrency | `ReentrantLock`, `ReentrantReadWriteLock`, `CompletableFuture`, `Executors`, `ForkJoinPool`, `LinkedBlockingQueue`, `ConcurrentLinkedQueue`, `Atomic*Array`, `ConcurrentHashMap.newKeySet` |
| Files / NIO | `FileChannel`, `FileLock`, `Path.resolve(String, String...)`, `Files.getFileStore`, `File.toPath` |
| Reflection / loaders | `ClassLoader.getResource(s)`, `Class.getModule`, `getGenericSuperclass`, `StackWalker`, `MethodHandles.lookup` |
| System / process | `System.load*`, `exit`, `getenv`, `Runtime.exec`, `addShutdownHook`, `maxMemory`, `ManagementFactory`, `Process` |
| Misc | `sun.misc.Unsafe`, `HexFormat`, `MessageDigest`, `UUID(long,long)`, `Locale.getScript`, `Math.fma`, `Thread.threadId`, `ScopedValue` |

Most of the Guava/JNA failures are consequences of the above (for example Guava segments extend
`ReentrantLock`).

LWJGL is not reported as missing: its Java classes are on the classpath, but they call native code.
That native layer is the shim work in Phase 3 and later, and is invisible to this analysis.

## Verdict
Feasible to continue. The missing set is small and well bounded, and each item can be handled with
a TeaVM class-library patch or a stub of our own. Not yet tested: whether the compiled output
runs (static analysis passing does not prove runtime correctness), startup size, memory use, and
the Worker threading design. Expect new errors to appear as each batch is fixed, because the
analysis only reports what is reachable from `Main` so far.

## Next
Phase 2: patch layer (our own replacements for the missing JDK classes), reproducible local build
script, and a first successful `.wasm` output.

## Phase 2 progress (in progress)

- New module `mc-web/classlib-ext/`: our own TeaVM class-library extension, written from scratch.
  Classes named `T<Name>` under `org.teavm.classlib.java...` replace the missing JDK classes.
  Done so far: `ReentrantLock`, `ReentrantReadWriteLock` (+ `Lock`, `Condition`, `ReadWriteLock`),
  `Future`, `FutureTask`, `ExecutorService`, `AbstractExecutorService`, `ThreadPoolExecutor`,
  `Executors`, `ForkJoinPool`, `ThreadFactory`, `ConcurrentLinkedQueue`, `LinkedBlockingQueue`,
  `TimeoutException`, `RejectedExecutionException`. Verified: the lock and Guava segment errors
  disappeared in the next TeaVM run.
- `log4j-core` and the log4j SLF4J binding are removed from the build (not needed in a browser).
- Heap: use `-Xmx11g`. A 24 GB setting gets the process killed on this 15 GB machine.
- Error count is 116 distinct items (was 125 after the first extension pass, 104 at the start).
  The count is not monotonic because fixing one layer lets TeaVM see the next.
- Remaining groups: `CompletableFuture`, atomic arrays, `LockSupport`, scheduled executors;
  `ClassLoader`/`Class`/`Package` resource and reflection methods; `System.exit/getenv/load*`,
  `Runtime.maxMemory/exec`; `File`/`NIO` channel methods; `Locale`, `UUID`, `Date`, `Character`,
  `Math` gaps; `java.net`/`javax.net.ssl` (HTTP, not needed offline); `sun.misc.Unsafe`
  (JOML, LWJGL, Guava); JNA internals; LWJGL `system` internals (the native shim, Phase 3).
- Each full compile takes about 8 minutes.

## Phase 2 status update

- **Analysis now passes with zero missing classes, methods or fields.** The 116 errors are gone.
- **Build speed:** `fastGlobalAnalysis = true` cuts the full compile from 8 to 37+ minutes down to
  about 1 minute for analysis (3 minutes when it continues into code generation). Heap `-Xmx11g`,
  thread stack `-Xss512m`.
- **Placeholder classes** (`classlib-ext/src/main/resources/mcweb/stub-classes.txt`, generated by
  `tools/genstubs.py` from the build log): sockets, selectors, crypto, `java.net.http`, JFR, OSGi,
  log4j 1.x and similar types that a browser singleplayer game never uses. Every member access on
  them is rewritten to a "not available in the browser port" error, so linking succeeds and only
  real use fails.
- **`JdkGapTransformer`** now also rewrites constructors and static field reads, for placeholders
  and for classes that inherit from one (netty's JFR events). TeaVM's own library classes only get
  explicit real shims, never generated stubs.
- **Current blocker:** after analysis, the WASM GC vtable builder throws a `NullPointerException`
  (a class's parent is missing from the final class set). A listener that forces parents to be
  reachable printed nothing, so the cause is later than reachability. Next step: reproduce with a
  small driver that calls the TeaVM tool directly so the offending class name can be printed.
- Real implementations still owed (currently stubs or throwing): `FileChannel` (OPFS, Phase 4),
  `Thread` constructors taking a `ThreadGroup`, `Class.getGenericSuperclass` (Gson `TypeToken`),
  `sun.misc.Unsafe` users (JOML, Netty, Guava).

## Phase 2 result: first `game.wasm`

- `mc-web/driver/` runs the TeaVM tool in-process on the game (`./run.sh out`, about 1 minute for
  analysis, 3.5 minutes through code generation) and prints TeaVM's own problem list. It also holds
  the diagnostics that found the blocker below.
- **Root cause of the vtable crash:** TeaVM 0.16's WASM GC vtable builder merges "trivial" tables.
  JNA's huge empty-interface web made `java.lang.Object`'s table collapse into an interface
  (`com.sun.jna.platform.unix.Reboot`), so Object looked non-concrete. A placeholder that was an
  interface in reality but declared as a class caused the same class of failure for `PathMatcher`.
- **Fix:** JNA, jna-platform and OSHI are removed from the build (native code; useless in a browser)
  and replaced by generated placeholders.
- **Result:** `game.wasm` is generated (about 200 MB; unoptimized, with debug info). TeaVM still
  reports 525 problems, all of one kind: native methods with no browser implementation.

| Native methods | Where | Plan |
|---|---|---|
| 204 | `org.lwjgl.system` (JNI, LibFFI, MemoryAccessJNI) | Phase 3 LWJGL shim |
| 115 | `org.lwjgl.opengl` (GL11C ... GL45C) | Phase 3: WebGL2 |
| 163 | `io.netty.channel` (epoll, kqueue, unix sockets) | drop the native transports |
| 20 | `com.mojang.jtracy` (profiler) | drop |
| 15 | `org.lwjgl.stb`, `lwjgl.util.vma`, text2speech, objc bridge | shim or drop |

## Phase 3 status: the game runs in a WebAssembly engine

- **Dropped for the browser:** Netty native transports, JNA, OSHI, jtracy (replaced by real no-op
  classes), text2speech (silent narrator), and every LWJGL jar (replaced by placeholders with their
  true class hierarchies, extracted from the real jars by `tools/stubinfo`).
- **Clean output:** `game.wasm` compiles with zero TeaVM problems (`driver/run.sh`), the oversized
  start function is split by `tools/wasmsplit.py` (V8 rejects any function over 7.6 MB), and the
  result validates in both Binaryen and V8 with zero errors.
- **Real bugs found and worked around** (all documented in the code):
  - `Object`'s vtable merged into a JNA interface (fixed by removing JNA).
  - TeaVM coroutine code-gen type error in two methods (`cut` list in `stub-classes.txt`).
  - TeaVM reflective-constructor helper ill-typed for `Fiber$Platform*` (constructor hidden).
  - My own field-fallback rewriter nulled real JDK constants (now limited to placeholders).
- **Running:** `tools/cycle.sh` rebuilds everything and runs the game in Node (same V8 as Chrome).
  Minecraft's `Main.main` starts, parses launch arguments (`org.teavm.mcweb.McWebMain`), prints its
  own crash report, and stops at **"Loading native libraries"**: the LWJGL layer.
- **Next:** implement `org.lwjgl.system` (memory, configuration, library loading), then SDL
  (window, input, events), OpenGL (WebGL2), shaders (shaderc/SPIR-V Cross stand-ins), stb, OpenAL.
- **Design notes for later:**
  - WASM GC objects cannot be shared between Web Workers. The planned integrated-server worker has
    to communicate by message passing, not shared memory.
  - Methods that can block (locks, `wait`, `Thread.sleep`) become TeaVM coroutines and spread
    through the call graph. Keep blocking primitives out of hot paths.
